# Storage 운영 절차

2026-10-27, 코드 리뷰 10-C에서 정했어요(10단계 결정 3·4). 앱이 지우지 못하는 Storage 파일을 사람이 정리하는 절차예요.

버킷 `covers`·`avatars`·`chapter-images`는 모두 **공개 버킷**이에요. 행이 더는 가리키지 않아도 파일이 남아 있으면 그 URL로 누구나 계속 열 수 있어요. 남은 파일을 정리하지 않으면 지운 줄 아는 프로필 사진이나 유료 책 이미지가 공개된 채로 남아요.

## 앱이 지우는 것

| 언제 | 지우는 것 | 코드 |
|---|---|---|
| 표지·소개 이미지 교체·삭제 | 행이 가리키던 옛 파일 | `lib/stored-image.ts` |
| 프로필 사진 교체·삭제 | 옛 파일 + 본인 폴더에서 10분 지난, 행이 가리키지 않는 파일 | `removeStaleAvatarFiles()` |
| 장 삭제 (응답 뒤) | `chapter-images/{bookId}/{chapterId}/` 중 다른 장 본문이 가리키지 않는 파일 | `removeChapterImages()` |
| 책 삭제 (응답 뒤) | `covers/{bookId}/` 전체 + `chapter-images/{bookId}/` 중 다른 책 본문이 가리키지 않는 파일 | `removeBookFiles()` |

지우지 못한 파일은 `[storage] 파일을 지우지 못했습니다` 또는 `[storage] 지워지지 않은 파일이 있습니다` 로그에 버킷과 경로가 남아요. Vercel 로그에서 이 문구로 찾아 대시보드(Storage)에서 지우세요.

## 사용자를 지우기 전 (결정 4)

앱에는 계정 삭제 경로가 없어요. 사용자는 Supabase 대시보드(Authentication → Users)에서만 지워요. 이때 `user_profiles`는 CASCADE로 사라지지만 **`avatars/{userId}/` 파일은 남아요.** 그 파일을 가리키는 행이 없어서 앱의 어떤 정리 경로도 이 파일을 찾지 못해요.

1. 그 사용자의 책이 있으면 먼저 앱에서(저자 계정으로) 책을 지워요. 그래야 `removeBookFiles()`가 표지·본문 이미지를 정리해요. `books.owner_id`는 `ON DELETE CASCADE`라 사용자를 바로 지워도 책 행은 함께 사라지지만, 그 경로로는 `covers/{bookId}/`·`chapter-images/{bookId}/` 파일이 남아요.
   - 판매 기록이 있는 책은 지울 수 없어요(`purchases`·`payment_transactions`의 `ON DELETE RESTRICT`). 이런 책이 하나라도 있으면 사용자 삭제도 FK 위반으로 거절돼요. 산 독자가 계속 읽어야 하므로 그 계정은 지우지 말고 사람이 판단하세요.
2. 대시보드 Storage → `avatars` 버킷에서 `{userId}` 폴더를 열어 파일을 전부 지워요.
3. 그다음 Authentication → Users에서 사용자를 지워요.

순서를 바꾸면 폴더 이름(사용자 ID·책 ID)을 다시 찾기 어려워요.

SQL 트리거로 `storage.objects` 행을 지우는 방식은 쓰지 않아요. 행만 사라지고 실제 파일은 남아요.

계정 삭제 기능을 앱에 만들게 되면 그 라우트에서 `avatars/{userId}/`를 비우세요.

## 본문 이미지 붙여 넣기 경쟁 (결정 3)

장 X의 이미지를 장 Y에 붙여 넣고 Y가 자동 저장되기 전에 X를 지우면, 정리는 그 파일을 "아무도 가리키지 않는다"고 보고 지워요. 그러면 Y는 저장된 뒤 깨진 이미지를 가져요. 정리가 DB에 저장된 본문만 보기 때문이에요.

지금은 장·책 삭제 라우트가 정리를 응답 뒤(`after()`)로 미루기만 해요. 그사이 Y의 자동 저장이 먼저 끝날 여지가 생겨요. 운영에서 깨진 본문 이미지가 실제로 보고되면 지연 삭제를 검토하세요. 지울 후보를 표에 넣고 하루 뒤 다시 검사하는 방식이에요.
